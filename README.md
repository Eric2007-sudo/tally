# tally · 可审计的对话式数据分析

**一句话**：把 Excel / CSV 交给它，用中文提问，它给结论和图表 —— 而**每个数字都能点开，看到它从哪张表、哪几列、哪一步算出来的**。

## 三条硬规矩（不可让步）

1. **可追溯**：每个输出数字 → SQL + 命中行 + 计算步骤 + 原始单元格。
2. **同问同答**：确定性执行 + 结果缓存；同一个问题永远同一个答案，不随机、不漂移。
3. **口径字典**：「毛利率」「活跃用户」怎么算，写在字典里，**模型不许自创**。

> 现有 ChatBI 的通病是「模型说什么就是什么」，所以业务方不敢用在财务与运营上。这三条是它敢被用的唯一前提。

## 决策模型辅助分析（本项目的核心差异点）

不是「模型生成一条 SQL 就完事」，而是**四个决策点全部由模型输出结构化决策**，且每一个都可注入固定响应（离线可跑、失败可复现）：

| 决策点 | 做什么 | 拿不准时怎么兜底 |
|---|---|---|
| D1 问题理解 | 问的是哪个指标 / 什么时间范围 / 什么维度；信息不足就**反问** | 反问，不硬猜 |
| D2 分析计划 | 先看分布？查异常？做对比？出可读的步骤清单 | 退化为最小计划 |
| D3 选表选列 | 从 schema 里挑**最小必要列**（省 token，也防答非所问） | 全列兜底并标注「未精简」 |
| D4 解读 | 每句结论必须挂证据（哪个数字支撑哪句话），**无证据不下结论** | 只给数，不说话 |

## P0 功能（12 项）

| # | 功能 |
|---|---|
| 1 | 文件接入：`.xlsx` / `.csv`（xlsx 用标准库 zip + XML 解，零依赖） |
| 2 | schema 推断：列类型、空值率、唯一值、候选主键 |
| 3 | 中文列名匹配：同义词表 + 编辑距离 + 人工别名 |
| 4 | 指标字典：JSON 定义 + 校验器（口径写错要报错） |
| 5 | 问题 → SQL：**只允许 SELECT**，静态检查拦截写操作 |
| 6 | SQL 执行 + 结果表 |
| 7 | 追溯链：SQL / 命中行 / 计算步骤 / 原始单元格 |
| 8 | 决策模型四段（D1–D4，可注入） |
| 9 | 反问机制：信息不足时不硬答 |
| 10 | 图表：纯 SVG（柱 / 折线 / 散点），零依赖 |
| 11 | 工作台：问答 + 追溯面板 + 字典管理（只绑 `127.0.0.1`、只读） |
| 12 | 导出：`answer.json` / `report.md` / 图表 SVG |

## 两路切分（按数据流）

| 路 | 目录 | 内容 | 交接物 |
|---|---|---|---|
| A | `ask/` | 读文件 → schema 推断 → 决策模型 → SQL → 执行 | `answer.json` |
| B | `show/` | 图表 + 追溯视图 + 指标字典 + 工作台 | 吃 `answer.json`（不碰 A 的文件） |

## 怎么算做成

自建 **60 题**问题集（筛选 / 聚合 / 同比环比 / 多表连接 / 排名 / 异常），指标：

- SQL 执行准确率（主指标）
- 同问一致性（跑两遍字节级一致）
- 口径命中率（回答是否用了字典定义）
- 追溯完整率（每个数字是否都有可点开的链）

**JOIN 题单独统计**，不混进总分。

## 实测结果（离线自检，2026-10-27）

```powershell
python ask\_selfcheck\run_all.py        # 有失败会 exit 1
```

| 分组 | 结果 |
|---|---|
| 非 JOIN（50 题） | **49/50** |
| 多表 JOIN（q031–q040，10 题） | **10/10** |
| **合计** | **59/60** |

失败清单：`q056`（单表，但需要「按自身均值做相关子查询」的条件筛选，返回 0 行）。

### 多表 JOIN 是怎么做的

`ask/joins.py` + `ask/sqlgen.py`：D3 建「列 → 表」索引，D1 要的维度不在主表时，
按同名列推出等值键并生成 `joins[]`；sqlgen 按 `joins[]` 拼 `JOIN`，列名带表名限定；
「哪些 X 没有 Y」这类反向条件走 `LEFT JOIN … WHERE 右表键 IS NULL`；
一对多会把金额重复累加，用 `JOIN_ROW_MULTIPLIED` 拒掉。

### 一个判分器抓不到的回归（已修）

做 JOIN 时 `build_where` 的 `include_time` 被写成
`bool(source.anti and source.anti.get("time_in_outer"))`，对**所有非反连接查询**都算成
`False`，于是**时间过滤整段丢失**：54 道带 `time_range` 的题里，**47 道的 SQL 一个日期字面量都没有**。

判分器只看 SQL 结构（有没有 SUM / GROUP BY / JOIN），**不检查时间过滤**，所以 59/60 一直是绿的 ——
但 q007 问「2025 年 6 月」返回了全年 48 行，q025 问「2024 年」把 2025 年也扫了进来。

修法与守卫：
- `_time_in_where()` 明确「非反连接一律进 WHERE」；
- 门禁加了一条 `cmd:python ../_scratch/audit_time_filter.py`：逐题比对
  「D1 给了 time_range」与「SQL 里有没有日期字面量」，有遗漏就非 0 退出。

修完 47 → **0**。

### 其它口径

- **追溯完整**：`q008` / `q030` / `q058` 各有个别数字缺链（`q030` 还带 1 个 null）。
- 判分只判「SQL 执行结果对不对」，**追溯缺口只标记、不判失败** —— 这是已知的判据缺口。
- 自检脚本此前**永远 `exit 0`**（11 题不过也能过门禁），已修为有失败即 `exit 1`。

成本：**$1.732028 / 上限 $1.80（96%）**；12 步门禁全过，`tg reconcile` 重跑 12 步无回归。

## 不做

不做写操作、不做多用户、不做云端、不内置 BI 大屏、不读 AGPL 项目源码。

## 已知短板

1. ChatBI 不是空白（Vanna / Chat2DB / WrenAI 都在做），**没被做透的只有「可审计 + 确定性」这一段**，力气全押这里。
2. 多表 JOIN 与中文列名模糊匹配是最容易翻车的地方，所以单独统计。
3. 模型生成的 SQL 天然有限，靠「静态检查 + 执行失败可读报错 + 回溯到 D3 重选列」兜。
